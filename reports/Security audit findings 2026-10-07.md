# Bucks security audit — verified findings (2026-10-07)

This is the permanent record of the security audit of the Bucks blockchain working tree, as it was on 2026-10-07 (before any fixes). Six auditors reviewed one area each, a build/test/probe agent ran the code, and a separate skeptic tried to disprove every finding. **No finding was refuted.** Severities below are the skeptics' final ratings. Many problems were found independently by several areas (for example the "every wallet gets the same key" bug appears as CRY-1, API-V1 and OPS-1, and the unvalidated fork path as CON-1, NET-1, NET-2, DB-1, DB-2 and API-V2), so the counts below are higher than the number of distinct problems (roughly 60 to 70). Line numbers refer to the code as it was *before* the fixes.

The *Planned phase* column shows where each finding is fixed: **1** = Phase 1 (already implemented in the working tree, being reviewed), **2a** = consensus & validation redesign, **2b** = storage, crash safety & locking, **3** = gold reserve module, **5** = network hardening, CI and dependency upgrades. Design documents for 2a/2b/3 are in `docs/design/`.

## Details

### API-1 — Loopback-trust auth plus wildcard CORS: any website, DNS-rebinding page or local process can steal the seed and drain the wallet

**Severity:** critical · **Area:** api-server-web · **Check result:** confirmed · **Where:** `src/server.cpp:713` · **Effort:** M · **Planned phase:** 1

isAuthorizedRequest (src/server.cpp:682-714) authorises every request whose remote_addr is 127.0.0.1 or ::1, with no token, cookie, Origin or Host check. The pre-routing handler adds `Access-Control-Allow-Origin: *` to every response (src/server.cpp:154-158) and answers every OPTIONS preflight with 200 (160-163). Handlers call json::parse(req.body) whatever the Content-Type, so a text/plain POST (a CORS 'simple request', no preflight) is processed. Route inventory: PUBLIC: GET /, static files, /api/status, /api/economy/status, /api/blockchain/info, /api/blocks/recent, /api/blocks/hash/*, /api/blocks/height/*, /api/transactions, /api/ipfs/pin/ls/*. ### NET-2 — Side-chain blocks persisted without validation and keyed by sender-chosen height, overwriting canonical rows

**Severity:** critical · **Area:** p2p-network · **Check result:** confirmed · **Where:** `src/blockchain.cpp:308` · **Effort:** L · **Planned phase:** 2a

When a received block's parent is known but its claimed work is not greater, addBlock saves it with blockDB->saveBlock(block) and returns true, with no validation at all (blockchain.cpp:308-312). No PoW, size or structure checks run, and the peer is not penalised. **Skeptic's evidence:** src/blockchain.cpp:277-313: if prevBlockHash is any in-memory non-tip block and forkWork <= currentWork, the block is saved with blockDB->saveBlock(block) (311) and the function returns true, with no checkBlock call. ### NET-V1 — Chain-work function returns 0 for every realistic difficulty, so honest nodes can never reorg and only unvalidated forged bits carry 'work'

**Severity:** high · **Area:** p2p-network · **Check result:** added by verifier · **Where:** `src/blockchain.cpp:28` · **Effort:** M · **Planned phase:** 5 (network/ops/deps)

workForBits computes shift = (exp-3)*8 and returns 0 whenever shift >= 64, that is for any compact exponent >= 11. POW_LIMIT_BITS is 0x1f00ffff (consensus.h:81, exponent 31), and adjustBits can never realistically push the exponent down to 10 or below, which would need a target under about 2^80. Every honest block therefore contributes 0 work and accumWork() of any real chain is 0. As a result: (a) the in-memory fork path compares forkWork (0) > currentWork (0), which is always false, so it never reorgs and just stores the side block (283-287, 308-312). (b) The DB fork path compares forkWork <= currentWork as 0 <= 0, prints 'ignoring' and returns true without even saving the block (257-259), so the next block on that branch has an unknown parent and is rejected (316), and the sender is penalised (network.cpp:445-448). (c) The only way to make forkWork exceed currentWork is to declare low-exponent bits. The in-memory path rejects those through checkBlock's expectedBits check, but the DB path never checks PoW or bits (see NET-1). The 'Bucks v1 security patch' that moved chain selection to accumulated work actually turned off honest chain selection entirely.

**How it can be exploited / fails:** Two honest miners find blocks at the same height, which is routine, especially with auto-mine on several nodes. Each node keeps its own block. Every later block from the other branch either fails to raise work above 0 or arrives with an unknown parent, so the nodes never converge. The network permanently splits into independent ledgers, and coins spent on one branch can be spent again on the other (cross-partition double spend). At the same time an attacker who sends a block with bits such as exponent 3, mantissa 1 through the DB path gets about UINT64_MAX of 'work' and wins every comparison.

**Recommended fix:** Compute work as 2^256 / (target+1) using 256-bit arithmetic (arith_uint256 / GetBlockProof style), decode compact bits with sign and overflow checks, and store cumulative nChainWork per validated header in a block-index tree. Only count work from headers that passed PoW against the contextually required bits. Add unit tests that compare the chain work of two branches at the real POW_LIMIT_BITS.

### NET-V2 — Reorg disconnect reverses gold markers without verifying the vault multisig, so a peer-forced reorg can zero or inflate the gold reserve

**Severity:** high · **Area:** p2p-network · **Check result:** added by verifier · **Where:** `src/blockchain.cpp:503` · **Effort:** S · **Planned phase:** 3

When a block is connected, gold injection and redemption OP_RETURN markers are applied only if validateVaultMultisig succeeds (blockchain.cpp:357-360); unsigned markers are skipped. Blockchain::disconnectTip (482-522) scans the same markers but never calls validateVaultMultisig. **Recommended fix:** Make connect and disconnect symmetric: record exactly which vault-verified gold events a block applied, for example in its undo data, and reverse only those on disconnect. **Skeptic's evidence:** Each ENCINIT triggers computeSharedSecret, an EC point multiplication with a new group (crypto.cpp ~404-421), and sends VERSION with no once-only guard (293-311). ### NET-9 — P2P encryption is unauthenticated, optional and can be re-keyed mid-session

**Severity:** medium · **Area:** p2p-network · **Check result:** confirmed · **Where:** `src/network.cpp:293` · **Effort:** L · **Planned phase:** 5 (network/ops/deps)

The ENCINIT exchange is anonymous ephemeral ECDH with no peer identity, signature, key confirmation or session-ID comparison, so an active man-in-the-middle can run separate sessions with each side. Encryption is not required. If a peer never sends ENCINIT, encryptionNegotiated stays false and every message type (BLOCK, INV, ADDR, GETADDR, VERACK) is processed in plaintext (280-288). No message is gated on handshake state, and VERACK alone marks a peer ACTIVE (335-338). ENCINIT is processed in plaintext even after negotiation (220, 280, 293-311): it replaces the session key and triggers an ECDH computation and a new VERSION each time.

**How it can be exploited / fails:** An on-path attacker (malicious ISP, Wi-Fi or hosting provider, BGP hijack) can strip ENCINIT so peers talk in plaintext, MITM the ECDH to read and modify all traffic, or inject a plaintext ENCINIT into an established session to switch it to a key the attacker knows. **Recommended fix:** Adopt BIP324 v2 transport (ElligatorSwift ECDH, HKDF-derived per-direction keys, ChaCha20-Poly1305 with encrypted length, session ID for optional out-of-band MITM detection), or at least: refuse unencrypted peers once v2 is supported, accept ENCINIT exactly once and before anything else, enforce a strict VERSION -> VERACK state machine, and optionally authenticate long-lived peers (BIP324 + manual peer keys).

**Skeptic's evidence:** ENCINIT carries a bare 33-byte pubkey with no signature or identity (293-311). If ENCINIT is never received, encryptionNegotiated stays false and every message is handled in plaintext (280-288). VERACK sets ACTIVE unconditionally (335-337). ENCINIT bypasses decryption (280) and is processed again even when encryptionNegotiated is already true. establishSharedSecret overwrites sessionKey (protocol_enc.cpp:18-24), so an injected ENCINIT re-keys the receiver to ECDH(node ephemeral key, attacker key), which the attacker can compute. The README claims 'End-to-end encrypted peer communication (ECDH + AES-256-CBC)' (README:19, 188), but the code uses unauthenticated anonymous ECDH with GCM.

There is no data-dir flag; every DB path is CWD-relative (include/blockchain.h:39).

**How it can be exploited / fails:** A remote peer floods messages to inflate logs and stdout I/O, a cheap DoS on disk and CPU. Unclean kill -9 shutdowns risk inconsistent SQLite and wallet state, and starting the node from a different directory silently creates a fresh chain and fresh wallets.

**Recommended fix:** Use std::atomic<bool> or sig_atomic_t, parse CLI arguments with validation, support multiple --connect and a --datadir, use log levels with rate limiting (as Bitcoin Core's -debug categories do), and shut down gracefully in the scripts.

### API-23 — Unused service worker with cache-first, never-versioned caching

**Severity:** info · **Area:** api-server-web · **Check result:** confirmed · **Where:** `web/sw.js:42` · **Effort:** S · **Planned phase:** 5 (network/ops/deps)

sw.js is never registered anywhere in web/ or frontend/. If it were, it would serve all non-/api requests cache-first, including cross-origin CDN scripts, from a constant cache 'bucks-wallet-v1' (lines 2, 42-56) that is never refreshed. manifest.json also references a missing screenshot.

**How it can be exploited / fails:** If the service worker is later enabled, a security fix to the JS is never delivered to existing users, and a once-poisoned CDN response stays cached indefinitely.

**Recommended fix:** Delete it, or use network-first with content-hashed asset names and a versioned cache, and never cache cross-origin scripts.

**Skeptic's evidence:** A grep for serviceWorker or sw.js registration across web/*.js, *.jsx, *.html and frontend/src finds nothing. web/sw.js is unregistered, and it is cache-first with a constant cache name.

### CRY-21 — Crypto tests have no known-answer vectors and hide failures

**Severity:** info · **Area:** crypto-wallet · **Check result:** confirmed · **Where:** `tests/unit/test_bip_8192.cpp:24` · **Effort:** M · **Planned phase:** 5 (network/ops/deps)

The mnemonic test treats WORDLIST_LOAD_FAILED as SUCCEED (tests/unit/test_bip_8192.cpp:24-25), which is exactly the failure behind CRY-1. The HD tests only check depth and length (tests/unit/test_hd_8192.cpp). There are no BIP-39/BIP-32-style known-answer vectors, no ECDSA malleability or low-S tests, no invalid-pubkey tests, and no fuzzing of the hex, Base58, DER and transaction parsers. ScriptInterpreter, including its broken OP_CHECKSIG, is dead code with no tests.

**How it can be exploited / fails:** Regressions like CRY-1, CRY-2 and CRY-6 pass CI and ship.

**Recommended fix:** Add known-answer vectors for every derivation step, negative tests (invalid pubkey, high-S, wrong sighash byte, replayed vault payload), round-trip serialisation-then-validation tests, and libFuzzer/OSS-Fuzz harnesses. Make a missing wordlist a test failure.

**Skeptic's evidence:** tests/unit/test_bip_8192.cpp:24-25 turns WORDLIST_LOAD_FAILED into SUCCEED, and the ValidationFailure test (lines 31-36) skips its assertions in the same case. That is why CRY-1 ships green. There are no known-answer vectors and no tests for invalid pubkeys, high-S or round-trip serialise-then-validate.

### GLD-12 — No tests for gold, vault or governance logic; low-S and strict-DER consensus flags are declared but unused

### NET-20 — P2P code paths are effectively untested (no state-machine, multi-peer or adversarial tests)

**Severity:** info · **Area:** p2p-network · **Check result:** confirmed · **Where:** `tests/perf_security/fuzz_protocol.cpp:7` · **Effort:** M · **Planned phase:** 5 (network/ops/deps)

### OPS-20 — No LICENSE, SECURITY.md or vulnerability disclosure process

**Severity:** info · **Area:** build-test-hygiene · **Check result:** probe/build-confirmed · **Where:** `README.md:265` · **Effort:** S · **Planned phase:** 5 (network/ops/deps)

## Build, test and probe results (before fixes)

### Build

Built the current working tree, not HEAD, out-of-tree in the scratch dir with `cmake -DCMAKE_BUILD_TYPE=Debug -DCMAKE_CXX_FLAGS="-Wall -Wextra"` and AppleClang 21 on arm64 macOS. CMake found Homebrew OpenSSL 3.6.2 (`brew --prefix openssl` points at a non-existent openssl@4, so detection fell back to openssl@3). googletest v1.14.0 was fetched via FetchContent. Targets bucks_core, bucks, unit_tests, integration_tests, system_tests and perf_security_tests all built with exit 0, 0 errors and 10 warnings. A stricter syntax-only pass (-Wconversion -Wsign-conversion -Wshorten-64-to-32 -Wshadow) gives 136 warnings: 106 sign-conversion, 18 shorten-64-to-32, 2 implicit-int-conversion. Three more scratch builds also succeeded: ASan+UBSan (AppleClang), libFuzzer+ASan+UBSan (Homebrew clang 22.1.7) and llvm source coverage.

Build-system notes:
- CMakeLists.txt and build.sh compile the same 20 sources, and both leave out src/miner.cpp. That file is tracked but does not compile (unknown type ConsensusParams, undeclared toHex), and its header include/miner.h is untracked.
- CMakeLists.txt now requires src/genesis.cpp, which is untracked. HEAD's CMakeLists hardcodes "C:/Program Files/OpenSSL-Win64", so a clean clone of HEAD does not build the code that actually runs.
- There is no default CMAKE_BUILD_TYPE, so builds are unoptimized and have no NDEBUG. Neither build path sets hardening flags (-fstack-protector-strong, -D_FORTIFY_SOURCE=2, -fPIE/-pie, RELRO/now, -fcf-protection or -mbranch-protection) or -Werror.
- The macOS binary is PIE and contains __stack_chk/__*_chk symbols only because Apple's toolchain adds them by default; Linux builds via build.sh (plain g++, no -O) get no guarantees.

### Tests

ctest reports 4/4 passing, but that is only 4 executables holding 15 gtest cases (unit 10, integration 2, system 1, perf_security 2). All 15 pass in both the normal and the ASan/UBSan build, and the suite takes about 3 s.

The green result is misleading:
1. BIP8192Test passes vacuously. It takes the SUCCEED() "skip" branch on WORDLIST_LOAD_FAILED (tests/unit/test_bip_8192.cpp:24-25), and in the current tree the wordlist never loads from any directory (see OPS-1). So the suite stays green while every wallet the node generates gets the same private key.
2. Most tests only check that something exists or did not crash. CryptoHash checks 2 bytes of SHA-256("hello"). HD8192 checks key sizes with no test vectors. FullNodeSystemTest never mines, despite its name. ServerNetworkTest only checks that the reply contains "HTTP/1.1", on a fixed port 8091, and Server::start() returns true even when bind fails (src/server.cpp:183-189).
3. The tests write a plaintext wallets.json into the current directory. Running the suite left a wallets.json in my scratch run dir; it holds the constant key.
4. No test covers ECDSA sign/verify, sighash, validation, reorg, mempool, PoW retarget, gold/governance multisig, server auth or P2P handling.

Coverage measured with llvm-cov over all 4 binaries: 32.9% of lines and 17.3% of branches across project sources. By file: network.cpp 8.2%, validation.cpp 11.7%, blockchain.cpp 13.2%, blockdb.cpp 24.4%, wallet.cpp 28.7%, bip_8192.cpp 31.3%, utxodb.cpp 34.5%, server.cpp 42.6% (mostly route registration). mempool.cpp, pow.cpp and script.cpp have no coverage at all.

The README's "comprehensive 4-phase test suite" and "Bucks has undergone extensive security testing: mempool bloat / Sybil / consensus theft / reorg" claims have no matching tests.

### Memory-safety checks

ASan+UBSan build (-fsanitize=address,undefined -fno-omit-frame-pointer -g): all 15 existing tests pass with no ASan or UBSan reports. That says little, because the tests barely touch the parsers or the consensus code. LeakSanitizer is not available on macOS arm64.

ASan did fire under my libFuzzer harnesses:
(1) heap-buffer-overflow READ in Bucks::NetMessage::deserialize at src/network.cpp:150. `24 + len` is computed in uint32 and wraps at line 148, so a len near 0xFFFFFFFF bypasses the size check and the vector constructor reads about 4 GB past the buffer. It is latent today because Peer::processBuffer rejects len > 4 MB first (network.cpp:254).
(2) An attacker-sized allocation of 241,229,627,392 bytes from vector::reserve(txCount) in Block::deserialize at src/block.cpp:237. txCount is an unchecked uint32 taken from peer block payloads (reached via network.cpp:421).

UBSan reported nothing. The byte-shift patterns such as data[i+3] << 24 are well-defined in C++17.

TSan was not run, so no concurrency testing exists. By code reading, server handlers take a Wallet* under walletMutex and use it after unlocking (src/server.cpp:478-487, 536-545), which races with /api/wallets/create push_back reallocations.

### Fuzzing

tests/perf_security/fuzz_protocol.cpp is not a real fuzzer. It is a gtest that feeds 1000 inputs of 0-1024 random bytes (mt19937, seed 42) to NetMessage::deserialize and catches all exceptions. It is not coverage-guided, has no corpus, and practically never gets past the 4-byte checksum, so it cannot reach the length-wrap bug. It ran inside ctest in under 1 s and passed.

I wrote scratch-only libFuzzer harnesses instead (Homebrew clang 22.1.7, -fsanitize=fuzzer,address,undefined, malloc_limit 512 MB) for six targets and ran each for about 25 s in parallel:
- NetMessage::deserialize: OOM on malloc(4294967295) after about 2.3k execs, at network.cpp:150. Replaying it without the malloc limit gives an ASan heap-buffer-overflow READ, so the length check is bypassable in the function itself.
- Block::deserialize: OOM on malloc(241 GB) after about 9.7k execs, at block.cpp:237 via reserve(txCount). This is reachable from P2P BLOCK messages. Release builds throw bad_alloc, which processBuffer catches, so it is a memory-DoS and robustness issue rather than a crash on most hosts.
- Transaction::deserialize: 766k execs, cov 577, clean.
- base58CheckDecode, base58Decode and parseHex: 964k execs, clean.
- verifyECDSA plus ECDH establishSharedSecret on attacker pubkeys: 215k execs, clean.
- AES-GCM P2PSessionEncryption::decrypt on attacker ciphertext: 2.9M execs, clean.

A 30 s fork-mode rerun with -ignore_ooms kept hitting the same two OOMs and found no new crash classes.

Recommendation: commit real libFuzzer/OSS-Fuzz targets for every network-reachable parser (NetMessage, Block, Transaction, INV/ADDR/VERSION payloads, OP_RETURN gold/governance marker parsing, mnemonic validation), with a corpus and CI runs.

### Live server probe

I copied the bucks binary into scratchpad/run, run2 and run3 and ran it from those directories with --server on random high ports (for example API 44423 and P2P 44424). Every node was killed via SIGINT within about 60 s, with a 75 s SIGKILL watchdog. Death was confirmed, no listeners remained, and the repo's blockchain.db and wallets.json were not touched.

Bind addresses (lsof): the HTTP API listens on 127.0.0.1 only. P2P listens on *:port (INADDR_ANY, network.cpp:605) with no option to restrict it.

GET endpoints: /api/status, /api/blockchain/info, /api/economy/status, /api/blocks/recent, /api/transactions and /api/mining/status return 200 with no auth. /metrics returns 404.

CORS: an OPTIONS preflight from Origin https://evil.example gets "Access-Control-Allow-Origin: *" and allows Authorization and X-API-Token. All responses carry ACAO * (server.cpp:155). The Host header is not validated (Host: evil.example gives 200), so DNS rebinding is possible.

Auth: isAuthorizedRequest trusts any connection from 127.0.0.1 (server.cpp:713), and the browser of whoever runs the node is such a connection. Cross-origin text/plain POSTs (CORS "simple" requests, so no preflight) with no token all reached their handlers:
- POST /api/wallets/create: 200
- POST /api/wallets/restore: 200, and it accepts any phrase
- POST /api/mining/mine: 200, a block was mined
- POST /api/transactions/send with a bogus sender: 400 "Sender wallet not found", meaning the handler ran with no 401

So any web page the operator visits can create, restore and spend wallets, sign messages, mine, and read /api/wallets and /api/wallets/primary (address, pubkey, balance, and the mnemonic when one is present).

Two critical bugs the probe confirmed:
(a) Every wallet created via the API had the same private key. Four independent processes produced one single key (root cause in OPS-1).
(b) POST /api/mining/mine {"minerWalletIndex":1} copy-assigns wallets[1] over wallets[0] (server.cpp:745,750). Wallet 0's key was destroyed and the loss was persisted to wallets.json at shutdown.

Other results:
- An 8 MB body to /api/anchor was rejected with 400, which is the httplib default limit (ServerConfig.maxRequestSize is never applied).
- The rate limiter allowed 79 of 130 rapid GETs, then returned 429.
- Path traversal (/../wallets.json, /%2e%2e/) returned 404.
- wallets.json was written in the working directory with mode 0644, containing privKeyHex and pubKeyHex in plaintext.
- About 100 DEBUG lines per mined block went to stdout.

I deliberately did not test the httplib negative chunk-size DoS (CVE-2026-45352) because it would exhaust memory on this machine.
